## [Unreleased]

### Added

- **Presentation "Documents on this page" restored via `mainDocuments`** (`apps/be/sanity.config.js`). Since stega encoding was disabled (`apps/fe/app/data/stega.ts` `enabled: false`), the visual-editing runtime finds no zero-width document markers in the DOM and the Presentation sidebar read "No matching documents" on every route. `presentationTool.resolve` now declares `mainDocuments` (`defineDocuments`): `/` → the `pageHome` singleton by type; `/:slug` → one GROQ filter mirroring `loadRouteContent()`'s resolution exactly — `detail` requires a slug match plus `allowRouting != false` (GROQ null-vs-false semantics match the JS `!== false` check), `pageContact`/`pageImprint` match their authored slug with the same `coalesce(...)` → `"contact"`/`"imprint"` fallbacks content.ts applies. Route → document now resolves without stega; the click-to-edit overlay decision is untouched. Known edge (commented in the config): a `detail` slugged `contact`/`imprint` beside an unauthored singleton is ambiguous here where the front end prefers detail — already a broken authoring state.

- **LQIP blur-up placeholders on every CMS image** (`apps/fe/app/data/{queries,content,image-url,stega}.ts`, `apps/fe/app/data/slices/{helpers,sliceImage,sliceImageWithText,slice2Up,slice3Up,sliceImageSlideshow}.ts`, `apps/fe/app/components/media/FigureBase.vue`). Every image projection now also pulls Sanity's `asset->metadata.lqip` — the ~20px-wide base64 preview Sanity computes at upload time — threaded through `PictureData`/`MediaData` (`lqip` field, empty string when absent) into `FigureBase`, which paints it as an inline `background-image` (cover-fit, centered) on the `<img>`/`<video>` element. The blurred placeholder shows the instant the box lays out and the opaque full-res pixels simply cover it on load — inline data, zero extra requests, no load-event JS. Covers (`coverLqip` on all three cover queries → `coverMedia()`) and all five image-bearing slices are wired. Both new result keys (`coverLqip`, `lqip`) added to `stega.ts`'s exclusion set (absolute rule #3 — a stega-tagged data URI corrupts the base64 payload inside a `style` attribute).

- **Dark-mode favicon variant** (`apps/be/schemaTypes/documents/site/siteOptions.js`, `apps/fe/app/data/{queries,content,stega}.ts`, `apps/fe/app/composables/usePageSeo.ts`). Studio: the Global Meta tab's `favicon` is relabeled **Favicon (Light Mode)** and gains a sibling `faviconDark` (**Favicon (Dark Mode)**, optional). Frontend: `siteOptionsQuery` projects `faviconDark.asset->url`, `SiteOptionsContent` carries it, and `usePageSeo`'s `<head>` link block emits scheme-aware icons — when both variants exist, two `rel="icon"` links with `(prefers-color-scheme: light)` / `(prefers-color-scheme: dark)` media queries (Chrome/Firefox swap the tab icon live with the OS theme; Safari ignores `media` on icon links and takes the last match); when only one exists it's emitted unconditionally, so a dark-only upload still beats the `/favicon.ico` fallback. The Apple touch icon never carries a media query (iOS reads exactly one) — it pins to the light asset, falling back to dark. `faviconDark` added to `stega.ts`'s exclusion set (absolute rule #3 — it's a CDN URL landing in a `<link href>`, where stega's zero-width characters would 404 the tab icon on preview builds).

- **Global Meta tab (favicon + OG image) and full per-page SEO wiring — canonicals, OG/Twitter tags, keywords, `<html lang>`** (`apps/be/schemaTypes/documents/site/siteOptions.js`, `apps/be/schemaTypes/documents/singletons/{pageContact,pageImprint}.js`, `apps/fe/app/data/{queries,content,stega}.ts`, `apps/fe/app/composables/usePageSeo.ts`, `apps/fe/app/pages/{index,[slug]}.vue`, `apps/fe/server/utils/site-url.ts`, `apps/fe/nuxt.config.ts`, `apps/fe/.env.example`). Studio: the Global document gains a **Meta** tab with `favicon` (tab icon, doubles as the Apple touch icon) and `ogImage` (site-wide default social-share image); Contact and Imprint gain the same per-page `seo` object (SEO tab) that Home and Detail already carried. Frontend: a shared `seoProjection` in `queries.ts` projects every document's `seo {metaDescription, metaKeywords, ogImage→url}` into the site-options, home, detail, contact, and imprint queries; `content.ts` normalizes it into a typed `SeoData` (new `resolveSeo()`) on `SiteOptionsContent` (which also gains `favicon`/`ogImage`/`language`) and on every `RouteContent` variant. `usePageSeo` — previously all placeholders (`https://example.com` canonical/og:url/og:image and eight icon links to `public/` files that never existed, every one a 404) — now emits the real thing: per-page **canonical + og:url** composed from `runtimeConfig.public.siteUrl` + the route path (home collapses to the bare origin, byte-matching sitemap.xml's own composition), **description/keywords/og:image** layered page-over-Global (image precedence: page SEO tab → Global Meta tab → Global SEO tab), **og:title/twitter:title** now the composed page title (was bare site title), `<html lang>` from the Global language code, the CMS **favicon** link (MIME-typed by extension) + apple-touch-icon, and empty-value tags omitted instead of rendered with `content=""`. `siteUrl` resolves through the same `resolveSiteUrl()` the sitemap/robots routes use, now preferring **`VERCEL_PROJECT_PRODUCTION_URL`** (`SITE_URL` → production domain → `VERCEL_URL`) so canonicals point at the Vercel production URL, not a per-deployment alias — head tags and crawler files can never disagree about the base URL. All five new result keys (`favicon`, `ogImage`, `metaDescription`, `metaKeywords`, `language`) added to `stega.ts`'s exclusion set (absolute rule #3 — they land in URLs and `<head>` attribute values, where stega's zero-width characters would corrupt the markup; `metaKeywords` is a bare `string[]`, covered by the existing array-index handling). Robots.txt and sitemap.xml verified configured: both prerendered into the static build via the existing `prerender:routes` registrations, robots allow-all + Sitemap line in prod / `Disallow: /` on preview builds, sitemap fed by the same `loadAllRoutePaths()` the router uses. Verified against a real `nuxt generate` with `SITE_URL` set: per-page canonical/og:url correct on home + detail, absolute sitemap/robots URLs, `lang="en"`, and the preview-code zero-bytes grep still returns nothing.

- **Ctrl+G dev-grid overlay ported to the Nuxt app** (`apps/fe/app/components/dev/DevGrid.client.vue`, `apps/fe/app/app.vue`). The old app's developer column-grid overlay (`routes/partials/grid.html` + the Ctrl+G branch of `src/app/index.ts`) was never carried across the Phase 5 cutover — its `.dev-grid`/`.dev-col` styles already lived in `styles/core/base.module.scss` (the "DEV GRID" block), but nothing rendered the markup or listened for the shortcut, so Ctrl+G did nothing. New `DevGrid.client.vue` renders the 24-column `.dev-grid` section and owns its own Ctrl+G keydown listener (registered in `onMounted`, removed in `onUnmounted`, same pattern as HomeAnimGui's Ctrl+F), toggling `is-active` via a reactive ref. Mounted once in `app.vue` as a sibling of `<main>` behind `v-if="import.meta.dev"` — combined with the `.client.vue` suffix, the overlay is dev-server-only and never ships in a production bundle. Verified against the running dev server with headless Chromium: overlay hidden on load (`display: none`), Ctrl+G shows it (`display: grid`, 24 cols tracking the live `--columns`/`--column-gap`/`--container-padding` vars), second Ctrl+G hides it again.

- **Mobile touch scroll reverted to native — `syncTouch` + 1.5x multiplier removed** (`apps/fe/app/plugins/lenis.client.ts`, comment/docs updates in `apps/fe/app/composables/useLenisScroll.ts`, `apps/fe/app/lib/scroll-restore.ts`, `apps/fe/app/controllers/home.ts`, `apps/fe/docs/animation.md`). Deliberately NOT a full revert to the old `$lenis = null` on mobile: the instance is kept as a passive mirror of native scroll (Lenis re-emits native scrolls and honours `scrollTo`), because `lib/scroll-restore.ts`'s mobile back-nav snapshot/restore — which the Close-as-back home-scroll feature depends on — and `useLenisScroll`'s single `$lenis.on("scroll")` path both need it. In image mode the overlay is `hidden` (zero rects), so the function now early-returns there and `runModeSwitch` forces a re-sync — after the DOM swap and scroll restore, while the pane is still faded out — when text mode returns. Rubber-band overscroll clamps to the first/last visible entry.

The blur-up `background-image` used to stay painted underneath the `<img>`/`<video>` forever, which was harmless only while the media sat at full opacity — anywhere the media animates below 1 (the home grid's image mode hover/entrance choreography) the stale LQIP bled through as a ghost background. `FigureBase` now tracks a `mediaLoaded` ref (img `@load` / video `@loadeddata`, plus an `onMounted` `complete`/`readyState` check so cache hits whose load event fired before hydration still clear) and drops the inline LQIP style entirely once the full-res pixels are in.

- **Mobile now runs Lenis with `syncTouch` and a touch speed multiplier** (`apps/fe/app/plugins/lenis.client.ts`, comment updates in `apps/fe/app/composables/useLenisScroll.ts`, `apps/fe/app/lib/scroll-restore.ts`, `apps/fe/app/controllers/home.ts`). - **Bottom-dwell auto-navigate-home jumped the scroll to top before (not after) the detail page faded out, and browser-back scroll restore silently landed at 0 instead of the saved position** (`apps/fe/app/transitions/default.ts`). - **Scrolling is now truly locked for the entire page transition, not just the entrance animation** (`apps/fe/src/app/controller/index.ts`, `apps/fe/docs/controller.md`, `packages/kido/src/native-scroller.ts`, kido `0.1.4` → `0.1.5`). - **Home→detail cover handoff no longer doubles the shadow on transparent covers** (`apps/fe/src/app/controller/transitions/home-to-detail.ts`, `apps/fe/src/routes/detail/detail.ts`). The shadow on the "Uselessly" cover is **baked into a transparent image asset** (no CSS shadow), so any two stacked visible copies composite their semi-transparent shadows into a **doubled/darker shadow**. The index→entry bridge left two such overlaps: **(A)** during the transition the original home reveal figure stayed visible (`HomePage.out()` keeps `.home__text-gpu` on screen) while the pixel-identical clone was stacked exactly over it, both coexisting until the home section is removed ~150ms in; and **(B)** in `DetailPage.in()` the real `.detail__cover` was held **solid** while the clone faded **down over it**. Both are now single-copy: (A) `out()` sets the original figure `visibility: hidden` the instant it clones it (instant, vs. the figure's 800ms opacity transition), so only the clone shows; (B) the cover is held **hidden** (`opacity: 0`) beneath the solid clone for the whole entrance, then clone and cover are **hard-swapped in a single frame** at the end — invisible because they are the same image at the same position, with no crossfade white-bleed. (B) is applied to both the active bridge path in `in()` and the dormant `mobileEntrance()` slide path (behind the `MOBILE_COVER_ENTRANCE_SLIDE` revert switch). Rationale comments in both files updated. Opaque covers are visually unchanged.

- **kido tab-visibility resume no longer corrupts in-flight animations** (`packages/kido/src/tab.ts`, `packages/kido/src/raf.ts`, kido `0.1.3` → `0.1.4`). On `visibilitychange → visible`, `Visibility` was handing subscribers `performance.now()` (an absolute timestamp) where the RAF hub expected the wall-clock **duration** the tab had been hidden. `RafHub._onResume` added that huge value to every live item's `startTime`, so any animation in flight when the tab was backgrounded/foregrounded (app-switch gesture, notification banner, lock/Face-ID prompt — all of which fire `visibilitychange`, especially on mobile) had its clock poisoned and snapped to its end or froze. This was the root cause of the intermittent "DIAA mark appears without fading in" glitch on return-to-home: a `visibilitychange` landing inside the 1200ms beat fade-in jumped it straight to opacity 1. `Visibility` now stamps `performance.now()` on hide and passes the elapsed hidden duration on resume (guarded to 0 on first-ever call and against negative skew); `RafHub._onResume` shifts only already-started items (`startTime !== 0`) so animations registered while hidden still initialize normally on their first visible frame. Both `onHidden`/`onVisible` are also now idempotent against duplicate same-state events. Requires no consumer changes — rebuild kido (`pnpm --filter kido build`, done).
